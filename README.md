# End-to-End Consumer Retention MLE & MLOps pipeline

[![CI](https://github.com/Zack-ai-data/retail-retention-mlops/actions/workflows/ci.yml/badge.svg)](https://github.com/Zack-ai-data/retail-retention-mlops/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

**consumer retail retention analytics on [UCI Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii)**

## Project Overview

 - Dataset: ~1.07M transactions from a UK online gift retailer (Dec 2009 - Dec 2011), spread over two Excel sheets (CC BY 4.0, UCI Machine Learning Repository).
 - Goal: help a retailer keep its customers. Turn raw transactions into customer segments (RFM), churn and lifetime-value predictions, then decide where to spend a retention budget, served through an API and a dashboard.
 - Stack: PostgreSQL, Docker, MLflow, Airflow, scikit-learn, FastAPI, Streamlit, Prometheus, Grafana, GitHub Actions.
 - Status: **steps 1-5 done** - Postgres in Docker, raw load, cleaned staging layer, customer feature/label snapshots with automated data quality checks, and three models (churn, 90-day customer value, RFM segments) tracked and registered in MLflow with a promotion quality gate. Lint, strict type checking, a coverage threshold and explicit error handling are in place (see Code quality). Batch scoring, an outreach optimizer with a random holdout, a FastAPI service and a Streamlit dashboard sit on top of the models. Airflow runs the pipeline as DAGs (ETL, then retraining and scoring). Monitoring is planned (see Roadmap).

Database layers (PostgreSQL, database `retail_dw`):
 - `raw`: untouched copy of the source (`raw.online_retail`), with `source_sheet` / `source_row` lineage.
 - `staging`: `staging.transactions`, cleaned and deduplicated, every row tagged with a `line_type`.
 - `marts`: `marts.customer_snapshots`, one row per customer per snapshot date with features and churn labels (plus `marts.snapshot_dates`), and `marts.customer_segments`, the latest RFM segment of every customer.
 - `ml`: predictions and monitoring data (planned). Experiments and the model registry live in MLflow, backed by their own `mlflow` database in the same Postgres.

Quickstart (needs Docker Desktop only, no local Python):
```
# 1. the dataset is already in data/online_retail_II.xlsx; create your env file
cp .env.example .env            # then change POSTGRES_PASSWORD
#    optional: record the commit on training runs (the image has no .git folder)
export GIT_SHA=$(git rev-parse HEAD)

# 2. start Postgres and the MLflow server
docker compose up -d postgres mlflow

# 3. run the pipeline: load Excel into raw (a few minutes), build staging + marts (~20 s),
#    train and register the models (~1-2 min)
docker compose run --rm app
#    or one stage at a time:
docker compose run --rm app python -m src.main --stage load
docker compose run --rm app python -m src.main --stage transform
docker compose run --rm app python -m src.main --stage train

docker compose run --rm quality python -m pytest

#    coverage threshold
docker compose run --rm quality
#    the dashboard's own tests (they need Streamlit, which only its image has)
docker compose run --rm dashboard-tests
```

Code quality (all configured in `pyproject.toml`, all run by `docker compose run --rm quality`, which exits non-zero if anything fails):
 - **Lint and format:** `ruff` (bug-finding, import order, modern syntax, simplifications) and `ruff format`.
 - **Types:** `mypy --strict` on `src/`.
 - **Tests:** unit tests; database-backed SQL tests on a throwaway Postgres; end-to-end tests that run the whole pipeline (load, transform, train) on a small synthetic workbook with the real file's two overlapping sheets; error-path tests; and regression tests that copy the loaded raw table into a scratch database, run the current cleaning and feature SQL on it, and check the known counts, line types, snapshot sizes and churn rates, and that re-training reproduces the recorded model results (they skip themselves if the real data is not loaded, or fail with `--require-warehouse`; update the expected numbers in the same commit as any intentional change to the cleaning or feature SQL). Marks: `-m e2e`, `-m warehouse`.
 - **Coverage:** branch coverage with a 90% minimum (98% when this was written). Mutation testing (a one-off, about 10 minutes, not part of the gate) killed 91% of the mutants made in 18 pure functions, using the faster tests only; the training, orchestration, database and SQL code were not mutated, so there is no mutation evidence for them either way.
 - **Error handling:** expected failures (missing or corrupt Excel file, database or MLflow unreachable, running a stage before its input exists, failed data quality checks) raise a specific error from `src/errors.py` with what happened and what to do; the command prints it without a traceback and exits with status 1. Unexpected errors keep their traceback and exit with status 2. The raw load is all-or-nothing, so a failed load leaves the previous data untouched. The database password is never printed.
 - **Workflow:** `CONTRIBUTING.md` defines what "done" means for any change (tests, a green `quality` run, updated regression values when results change on purpose) and what a green run does and does not prove.
 - **Releases:** tagging a green commit on `main` (for example `v0.1.0`) builds the API and dashboard images, starts each to check it runs as a non-root user, and publishes them to the GitHub Container Registry with the version and commit as tags. The commit is built into the API image so training runs record which code produced them. Running the images on a host (staging, then production) comes after the pipeline is complete; see CONTRIBUTING.md.
 - **Dependency updates:** Dependabot (`.github/dependabot.yml`) opens a pull request each Tuesday at 10:00 Malaysia time when a GitHub Action, a base image in a Dockerfile or an image in `docker-compose.yml` has a newer version. CI runs on every one and a pull request cannot merge unless it passes. It is deliberately kept away from anything that would turn a version bump into a migration: it never proposes a major version of Postgres (the existing data volume would not open), Redis, Prometheus, Grafana or Airflow, and never a different Python for the base images, because the lock files are hash-pinned wheels built for Python 3.12. It does not touch the Python libraries at all: they are locked by hash and regenerated on purpose (see CONTRIBUTING.md). Dependabot **alerts** (a warning when a dependency version has a known vulnerability) and secret scanning are switched on in the repository's settings; GitHub's dependency graph reads `pyproject.toml` and the workflows but not the `.lock` files, so an alert for one of the locked library versions would not be raised, a known gap. Tests check that every Dockerfile folder and every compose image is covered and that none can jump a major version. Whether GitHub accepts the file and opens its first pull requests can only be seen after it reaches `main` (Insights > Dependency graph > Dependabot).
 - **Continuous integration:** `.github/workflows/ci.yml` runs on GitHub Actions. On every push and pull request, `quality` (lint, format check, strict types, the fast tests with the 90% coverage floor) and `dashboard` (the Streamlit tests) must pass before a change can merge to `main`, which is protected. `airflow-dags` builds the Airflow image and loads every DAG in it; it is advisory for now. After a merge, `full-training` repeats the tests with the real hyperparameter grids and `regression` loads the real dataset and checks that the pinned results reproduce. Training tests use one hyperparameter combination and 100 bootstrap resamples by default (about 11 minutes instead of 23); see CONTRIBUTING.md. The workflow ran green on its first run on GitHub. **Every Monday at 10:00 Malaysia time (02:00 UTC) all five jobs also run on a schedule.** Nothing in the repository has to change for that run to go red: what it can catch is what is not pinned (the Docker images, the runner image and the actions move on their own, while the Python libraries are locked by hash and cannot). It is a reproducibility check and not retraining, because the dataset is static, so the results should come out the same each week. It runs on GitHub's machines with their own throwaway Postgres and MLflow, never your laptop's stack, and keeps nothing after the run. GitHub switches scheduled workflows off after 60 days without any activity in the repository (re-enable them under Actions) and may start a run some minutes late; it is free because the repository is public and it uses no secret; a failed run emails whoever last changed the schedule line, if their notification settings allow it. The schedule has its own concurrency group, so a push to `main` cannot cancel it. The trigger can only be exercised by GitHub's clock after the change reaches `main`; until the first Monday run, what is verified is the schedule's setting (pinned by tests) and that the jobs it runs pass when started by hand from the Actions tab.
 - **Reproducibility:** exact library versions, with hashes, are pinned in `requirements.lock` (runtime) and `requirements-dev.lock` (plus test tools); the Docker images and CI install from them, and a test checks the installed versions match. Every training run is tagged with the git commit, the checksum of the Excel file that was loaded, a checksum of the transform SQL, the lock file checksum and the library versions, and logs the datasets it used, so a model in the registry can be traced to what produced it.
 - **Packaging:** the `app` image is runtime-only and runs as a non-root user; tests and dev tools are in the separate `quality` image. A saved model loads without importing the training code, matplotlib or the database driver (tested in a fresh interpreter), which is what lets the API image stay small.

Data notes and cleaning decisions (`sql/transform/010_staging_transactions.sql`):
 - **Sheet overlap:** the two sheets share 2010-12-01 to 2010-12-09 as an exact copy (22,523 rows, 1,088 invoices, identical line counts). Each invoice is kept from the earliest sheet only. A quality check proves every dropped row has an identical kept twin.
 - **Repeated lines inside one sheet** (about 12k rows) look like genuine repeat scans, e.g. 20 lines of quantity 1 on one invoice. They are kept and flagged `is_repeated_line`, not deleted.
 - **Nothing is dropped for being odd.** Each row gets a `line_type` so downstream code chooses what to use and counts always reconcile with raw:
   `sale` (quantity and price > 0), `return` (invoice starts with `C`), `non_product` (postage, fees, discounts, manual entries, vouchers, test items), `stock_adjustment` (write-offs and zero-price lines, nearly all with no customer), `adjustment` (invoice starts with `A`; in this data those rows use the bad-debt code `B`, so they land in `non_product`).
 - About 22% of sale lines have no customer id, so customer-level features cover the ~78% of lines where the customer is known.
 - Prices can be negative or zero and customers can span several countries; features use the most recent country.

Retention modelling setup (`sql/transform/020_marts_customer_snapshots.sql`):
 - **Money is net of returns.** A cancelled order must not count as a purchase: one customer's £77,183.60 order was cancelled the same day, which had made them the best "retained" customer in the data. `monetary` is sales minus returns to date (`gross_sales` keeps the gross figure), `spend_last_90d` is net, and `return_rate` is the share of gross sales returned.
 - **Churn definition:** a customer is churned at a snapshot date if they have no net-positive spend (sales minus returns, never below zero) in the following 90 days. Only customers with at least one prior purchase are included.
 - **No leakage:** features use only purchases strictly before the snapshot date; `label_*` columns use only the 90 days after it.
 - **Time-based split:** eight snapshots exactly 90 days apart. Six train (2010-03-18 to 2011-06-11), one tests (2011-09-09), so a model is always tested on a later period than it trained on. The earlier snapshots matter because they include the previous year's pre-Christmas period (2010-09-14). A final `score` snapshot (2011-12-10) describes every customer as of the end of the data; it has no labels (its future is unknown) and is what deployed models score.
 - **Fixed-window features:** model inputs describe the 365 days before each snapshot (`*_365d`), so every snapshot is measured the same way even though the data holds only 3 months of history at the first snapshot and 21 at the test snapshot. `history_days_available` (capped at 365) says how much of the window exists, and `season_sin` / `season_cos` encode the time of year. Lifetime columns (`frequency`, `monetary`, ...) are kept for segmentation.
 - **Actionable population:** the churn and value models train, are gated and report on customers who bought within the last 180 days (`is_actionable`; 53% of customers at the test snapshot). Customers silent for longer are lapsed, a reactivation problem where churn is close to certain (77-90% in every snapshot), and including them flattered every headline number: they are easy to rank by recency alone. The 180-day threshold is two horizons and was chosen from the campaign logic, not tuned on the test snapshot (though I had already seen full-population test results when I chose it). Scoring a lapsed customer with these models is outside what they were trained for.
 - **Features:** recency, frequency, net monetary value, tenure, average order value, average days between orders, distinct products, recent order trend, returns, country.
 - **Worth knowing:** churn runs 40-70% across snapshots (40% in March 2010, 53% in June, 43% in September, 70% in December 2010, 65%, 68%, then 57% in the test snapshot) because the pre-Christmas buying peak shifts who buys in the following 90 days. That distribution shift is a useful monitoring case later.

Data quality checks (run after every transform, the pipeline fails if any fails): dropped rows have identical twins, each invoice comes from one sheet, every row has a line type, features never use data on or after the snapshot date, histories are consistent, only the score snapshot is unlabelled, no customer is labelled retained without positive net spend in the window, and every label window ends inside the available data. Transform, checks and publication happen in one transaction: if a check fails, the previous staging and marts tables are left unchanged.

Modeling (`src/model.py`, tracked in MLflow experiment `retail-retention`):
 - **Selection without peeking:** candidate algorithms and hyperparameters are compared by expanding-window cross-validation over the training snapshots only (train on earlier snapshots, validate on the next one). The test snapshot is not used to choose models or hyperparameters; it is used to report results and by the promotion gate, and the value model's objective was changed once after its first test result had been seen (the change was motivated by cross-validation on the training snapshots).
 - **Churn classifier** (`retail-churn-classifier`): chosen between logistic regression and gradient boosting by cross-validated PR-AUC; gradient boosting is currently selected. On the actionable test customers (churn rate 0.39): ROC-AUC 0.772, PR-AUC 0.652 (1.68x the no-skill rate) against 0.657 / 0.535 for ranking customers by recency alone. The PR-AUC gain is +0.118 with a 95% bootstrap interval of +0.089 to +0.144, and it is significant at all four backtest origins (2010-12-13 to 2011-09-09, each trained only on snapshots whose label window had ended). Among the 20% of customers scored highest, 70.6% churn, against 60.2% when ranking by recency, and the model finds 36.5% of all churners against 31.1%. By band, PR-AUC is 0.554 against 0.391 among customers who bought in the last 90 days, and 0.734 against 0.611 among those who last bought 91-180 days ago. The BG/NBD statistical baseline (probability a customer is still active, fitted before the test snapshot) scores PR-AUC 0.439: it treats every one-time buyer as active, so it does not rank them. The same model scored 0.821 / 0.799 on the whole population before the population was restricted, which was mostly the lapsed customers being easy to rank.
 - **Calibration:** on the actionable test customers the model expects 47% to churn against 39% observed (calibration error 0.087, Brier 0.195). A Platt calibrator is fitted on out-of-fold predictions and kept only if it improves log loss on the latest cross-validation snapshot; here it did not, so the model is uncalibrated. A first version applied it unconditionally and made the test result worse (error 0.148), because churn depends on the season and a mapping learned from other periods does not fit the pre-Christmas window. Probabilities still run high, which is one reason retraining and drift monitoring are in the roadmap.
 - **90-day value model** (`retail-value-regressor`): a two-part (hurdle) model, expected spend = P(buy) x E[spend | buy]. P(buy) is one minus the churn model's churn probability, so churn and value cannot disagree about who is likely to buy. E[spend | buy] is a gamma-loss regressor trained only on customers who bought, selected by cross-validated gamma deviance. A single-stage Poisson model is trained alongside for comparison only. Lessons learned: a first version trained on log(spend) underestimated total spend by 78% in cross-validation, and absolute-error loss collapses to predicting zero for the many non-buyers. The two-part model ranks customers exactly as well as the single-stage one (Spearman 0.592 vs 0.592) and is slightly more biased (-31.8% vs -30.9%), so it adds explanation, not accuracy. It shows where the bias comes from: in the test window the model expects 53% of customers to buy (61% did) and buyers to spend 1,068 (they spent 1,423), a seasonal level shift that the previous year's snapshots only partly capture.
 - **Quality gate** (`src/gate.py`, rules in `docs/problem_statement.md`): a new model version becomes the `champion` (what the API will serve) only if every check passes, and the decision with all its evidence is stored as a tag on the model version and the run (and as `gate.json`). The current champion is loaded and re-scored on the same data as the candidate, rather than trusting the metric it logged when it was trained; a champion trained on different feature columns is reported as not comparable. **Churn** must beat ranking by recency with a bootstrap interval that excludes 0, on the test snapshot and on most backtest origins, and must not be worse than the champion. **Value** must rank customers better than the naive "next 90 days = last 90 days" forecast (Spearman interval excludes 0), capture at least as much spend in the top decile, have a total bias within 40% of actual spend, and not be significantly worse on RMSE with spend capped at the 99th percentile of training spend (so a few wholesale accounts cannot decide it). On the current data both pass. The 40% bias bound is a sanity limit, confirmed by the project owner. It was set **after** seeing that the value model is 31.8% low in the pre-Christmas test window (the naive forecast is 27.0% low); an earlier rule, "no more biased than the naive forecast", rejected the model by 4.8 points. The bound is an assumption to revisit as more seasons of data arrive. **Registry after the retrain on 2026-10-19:** churn v2 is the champion (v1 was trained on different feature columns, so it could not be re-scored and was recorded as not comparable); value v2 is the first value champion (v1 stays in the registry as the rejected attempt); segments v2 is the champion.
 - **RFM segments** (`retail-rfm-segments`): KMeans on log-scaled recency, frequency and monetary value as of the score snapshot, k chosen by silhouette (k=4). Written to `marts.customer_segments`. The largest group, "High value / Active", is 20% of customers and 74% of revenue; "High value / Lapsed" (25% of customers, about 230 days since their last order) is the win-back target.
 - Models are saved with cloudpickle, so only load models from this project's own MLflow registry. A pickle needs the library versions that produced it, which is why they are pinned and recorded on each run. (MLflow's safer `skops` format was not adopted: the custom model classes would each need an explicit trust list.)

Serving and decisions (step 4):
 - **Margin at risk** (`src/scoring.py`): `P(churn) x spend if the customer buys x 30% margin`. "Spend if they buy" is the second stage of the value model, not the 90-day forecast, which already includes the chance of not buying and would count it twice. It is an upper bound on what contacting a customer could save: the project has no campaign data, so it ranks who is at risk and does not claim who can be saved.
 - **Only customers the models were trained for are scored** (bought within the last 180 days). Asking about a lapsed customer is an explained error that points to the win-back list, not a meaningless number.
 - **Stored and live scores, deliberately both.** Batch scoring writes `ml.predictions` (every run is kept, with the model versions): reliable, auditable, and the list the outreach plan is made from. The API can also score a customer live with the champion models, or score features you send for a what-if question. Both call the same function, and a test checks that for the same model versions the table and the API give the same numbers. Live scoring does not make a customer's inputs fresher: features are as of the latest snapshot.
 - **Outreach plan** (`src/optimizer.py`, tables `ml.outreach_plans` and `ml.outreach_assignments`): rank by margin at risk, take the top 500 whose margin at risk exceeds the £5 contact cost, and hold out a random 10% (fixed seed, stored) who are deliberately not contacted, so that impact could be measured later. The 500 and the £5 and 30% are stated assumptions (`docs/problem_statement.md`).
 - **On the real data** (3,471 customers scored as of 2011-12-10): the plan contacts 450 customers, holds out 50, costs £2,250 and covers £83,271 of margin at risk. **Every one of the 3,471 customers clears the £5 contact cost** (margin at risk averages about £83, £286,419 in total), so the cost never limits the list and the fixed number of customers decides it. The Assumptions page of the dashboard shows this.
 - **API** (`src/api.py`, FastAPI, interactive docs at `/docs`): `GET /health`, `GET /customers/{id}/score` (live), `GET /customers/{id}/prediction` (stored), `GET /customers/{id}/features`, `POST /score` (what-if), `GET /outreach/latest`, `GET /outreach/sensitivity`, `POST /models/reload`. Inputs are validated, the customer id is a bound query parameter, errors say what to do, and a database failure never includes the password. Models are loaded once at startup (a failure shows as a clear 503, not a crash) and can be reloaded without a restart. Every answer carries the model versions.
 - **Dashboard** (`services/dashboard/`, Streamlit): who to contact (with a CSV download of the contact group only, never the holdout), customer lookup (live next to stored), what-if, and the assumptions. It talks only to the API, runs in its own small image with its own pinned dependencies, and none of the training stack. Its logic is in `src/dashboard_client.py` and tested without Streamlit; the pages are tested with Streamlit's test runner against a fake API, and were also driven against the live API and real data.
 - **Not yet:** authentication (everything is bound to localhost), a clock-based schedule (the Airflow DAGs run when started by hand or when the ETL DAG finishes, because the data does not change), and monitoring of the stored predictions (step 6).

Orchestration (step 5):
 - **Airflow 3.3.2 with the Celery executor and Redis**, started with `docker compose --profile airflow up -d airflow-apiserver airflow-scheduler airflow-dag-processor airflow-worker airflow-triggerer` (the `airflow` profile keeps it out of a plain `up`). The scheduler queues tasks in Redis and the worker runs them. The interface is at `http://localhost:8080` (localhost only); log in with `AIRFLOW_ADMIN_USER` and `AIRFLOW_ADMIN_PASSWORD` from `.env`. Stop it with `docker compose --profile airflow stop`.
 - **The pipeline is inside the Airflow image, in its own Python environment.** The image holds two environments on purpose: Airflow's own, with the library versions Airflow tests together, and `/opt/pipeline-venv`, built from this project's hashed lock file. Tasks run `/opt/pipeline-venv/bin/python -m src.main --stage ...`, so the pipeline runs on exactly the library versions the tests ran with (Airflow itself pins pandas 3.0.5 and numpy 2.5.3; the project is tested on 3.0.6 and 2.5.4). The image is large (about 4 GB).
 - **Secrets come from `.env`, never from defaults.** The Airflow login, the key that encrypts stored connections and the key that signs tokens between services must be set (see `.env.example`); the `airflow-init` service refuses to run without them, and it checks that the database and the admin user really exist before anything else starts. The database URL is built from the existing `POSTGRES_*` settings by `services/airflow/db_url.py`, so the password is stored once and may contain special characters. Airflow's metadata lives in the `airflow` database of the same Postgres.
 - **`pipeline_healthcheck`** is a DAG you run by hand (`docker compose --profile airflow exec airflow-scheduler airflow dags trigger pipeline_healthcheck`). It does no data work. It proves, through the Celery worker, that the pipeline's environment works, its command line starts, and Postgres and MLflow are reachable from where tasks run.
 - **`retail_etl`** runs `load_raw` then `transform_marts` (staging, customer features, labels and the data quality checks, published in one transaction or not at all). Trigger it with `docker compose --profile airflow exec airflow-scheduler airflow dags trigger retail_etl`. It has no schedule, because the dataset does not change and a schedule would reload the same file. The load is retried once; a failed quality check is not retried, because the same data would fail the same way. When the transform succeeds the DAG records that the `customer_snapshots` Asset was refreshed, which the retraining DAG will wait for. Each task is one pipeline stage, built by `services/airflow/dags/pipeline_common.py`, which rejects an unknown stage name when the DAG is loaded.
 - **`retail_retrain_score`** starts by itself when `retail_etl` has refreshed `customer_snapshots` (an Asset), or by hand (`... airflow dags trigger retail_retrain_score`). It runs `train`, then `report_promotion` and `score` side by side, then `plan` after `score`. The promotion gate rejecting a new model is a normal result, not a failure: the previous champion keeps serving, so `train` succeeds either way, which a scheduler cannot tell from a promotion. `report_promotion` (the `report` stage) reads the gate's recorded decisions back and logs one line per model; if any model was not promoted it exits 99, which Airflow shows as **skipped** (yellow) with the reason in the log, and `score` and `plan` carry on with the live models. A version with no recorded decision, an unknown decision format, or a champion alias moved after training fails the task instead. `monitor` runs after `plan` and refreshes the aggregate tables the Grafana dashboards read (see Monitoring below). `train`, `score`, `plan` and `monitor` are retried once (`score`, `plan` and `monitor` write in one transaction, so a failed attempt leaves nothing behind; each successful `plan` adds a row to `ml.outreach_plans`); the report is not retried.
 - **If only some models are promoted** (for example churn is, value is not), scoring uses each model's live champion and records both versions in `ml.scoring_runs`. The value model carries its own copy of the churn model it was trained with, so `p_churn` and `margin_at_risk` use the new churn champion while the stored `expected_spend` still uses the older churn model inside the live value model, and no longer equals (1 - `p_churn`) x `spend_if_retained`. `expected_spend` is shown in the API and dashboard but never used to rank customers, and `tests/test_scoring.py` pins this behaviour.
 - **Build the Airflow image with the commit if you want runs to record it:** `export GIT_SHA=$(git rev-parse HEAD)` before `docker compose --profile airflow build`. Without it the image records `unknown` and training runs started by Airflow log `git unknown` (training itself is unaffected).
 - **Checked by running it:** a cold start brings all six services to healthy (about 1.5 GB of memory), the health-check DAG's four tasks run through the Celery worker, and a task confirmed the pipeline environment reports the locked versions. A full `retail_etl` run took about 2.5 minutes (load 100 s, transform 23 s), passed all nine data quality checks, and left the warehouse tables identical in content (same raw and feature-table fingerprints); only `raw.load_log` gained a row. `services/airflow/check_dags.py` loads every DAG as Airflow does and fails on an import error, and it fails on a deliberately mistyped stage name.
 - **In CI:** the `airflow-dags` job builds the image and runs `check_dags.py` on every pull request (advisory, not a required check yet). It passed on its first two runs on GitHub (about 3.5 minutes each).
 - **Retraining DAG, checked on the real data:** one run through Airflow and the Celery worker took about 3 minutes (train 2 min 22 s). All three models went from version 3 to version 4 and were promoted, with the same metrics as before (churn PR-AUC 0.652 against the recency baseline's 0.535; value Spearman 0.592 against 0.440). Scoring run 2 matched run 1 exactly on all 3,471 customers (largest difference 0 in churn probability, spend and margin at risk), and plan 2 selected the same 500 customers as plan 1 (same seed). A second run was started only by triggering `retail_etl`: the retraining DAG started by itself (run type `asset_triggered`) in the same second the transform finished, its four tasks succeeded, the models went to version 5 with the same decisions, and scoring run 3 matched run 2 exactly (plan 3 selected the same 500 customers). A rejection has not happened in a real run, because the gate promoted every model. That path is covered two ways: the report logic is tested against a real model registry, and a throwaway DAG with the same operator settings confirmed in Airflow that a task exiting 99 ends as skipped while `score` and `plan` still succeed and the run is marked success.
 - **Not yet:** failure alerts and the time since a model was last promoted are part of step 6 (Monitoring, below).

Monitoring (step 6, in progress):
 - **Started with** `docker compose --profile monitoring up -d` (the `monitoring` profile keeps it out of a plain `up`; start the API too so there is something to scrape: `docker compose up -d api`). Grafana is at `http://localhost:3000` (log in with `GRAFANA_ADMIN_USER` and `GRAFANA_ADMIN_PASSWORD` from `.env`; Grafana's built-in `admin/admin` is never used, because it refuses to start with an empty password), Prometheus at `http://localhost:9090`. Both are bound to localhost, run pinned image versions, and add roughly 140 MB of memory together. To stop only monitoring: `docker compose stop grafana prometheus` (`docker compose --profile monitoring stop` also stops Postgres and MLflow, which are in the default set).
 - **The API exposes `GET /metrics`** (`src/metrics.py`): requests, latency and failures per route, requests in progress, and the version of each champion model it is serving. Routes are labelled by their template (`/customers/{customer_id}/score`), never by the URL that was requested, so a customer id can never become a metric label or create a time series of its own. The served-version gauge shows something that was invisible before: the API loads the champions at start-up and on `POST /models/reload`, so after a retrain promotes a new champion it keeps serving the old one until it is reloaded.
 - **Grafana reads Postgres directly** (the warehouse, Airflow's and MLflow's databases), through `grafana_ro`, a login that can only read. It is created by the `grafana-db-init` job (repeatable; Postgres only runs `sql/init` on a brand-new volume) from `services/grafana/db/readonly_user.sql`, with the password from `.env`. It has named tables and, in the Airflow and MLflow databases, named columns only: in the warehouse only the scoring-run log and the aggregate `ml.monitor_*` tables (no customer-level data), and in the other two no Airflow connections or variables or run arguments and no MLflow artifact paths. The job grants only what exists and lists what it skipped, so it succeeds on a new machine before Airflow or the pipeline has ever run; run it again (`docker compose --profile monitoring up grafana-db-init`) once they have. A column that no longer exists (after an upgrade) is an error, not a silent skip. Prometheus is only needed for the API's own metrics.
 - **Everything Grafana shows is a file in the repository** (`services/grafana/`): the data sources and the dashboards are loaded at start-up from read-only mounts, so a fresh start gives the same Grafana. Three dashboards: **Retail API** (traffic, latency, and the model version the API is serving beside the champion in the MLflow registry, so a gap between them is visible), **Customers and churn** (churn rate, 90-day spend and customer counts by snapshot, how the latest scores are spread, margin at risk by score bucket, segment sizes) and **Models** (every version and what the gate decided; the churn model against the recency and BG/NBD baselines; its gain over the recency baseline at each backtest origin with its 95% interval; calibration error; the value model's rank correlation and bias; segmentation quality). The data dashboards use the dataset's own dates (2010 to 2011), and the version charts leave out versions that were evaluated before the baseline comparison existed, because their numbers would not compare. **Grafana loads these files when it starts and did not notice edits while running on this Windows setup, so after changing a dashboard or provisioning file run `docker compose restart grafana`.**
 - **The `monitor` stage** (`python -m src.main --stage monitor`, part of `--stage all`, and the last task of `retail_retrain_score`) writes seven small aggregate tables, `ml.monitor_*` (`src/monitoring.py`, `sql/schema/005_ml_monitoring.sql` and `006_ml_monitoring_drift.sql`): per-snapshot customers, churn rate and spend; the score distribution of every scoring run; segment sizes; drift (below); every model version with the gate's decision; every logged metric; and the churn backtest per origin (read from the artifact training saves, since MLflow does not keep it as a metric). They are plain tables replaced as a whole in one transaction, not views: the transform stage drops and rebuilds the marts tables on every run, which a view over them would block (`DROP TABLE` without `CASCADE`) or silently lose. Dashboards therefore never read a customer row, and what they can show is fixed in tested code. Every dashboard query that reads the warehouse is run against a real test database in the test suite.
 - **Checked by running it** on the real stack: Prometheus scraped the API (both targets up); all four Grafana data sources reported a working connection; the dashboard loaded; a query through Grafana to MLflow's database returned the registry champion (version 5), matching the version the API served. The read-only login was tried with 37 actions: the 7 reads it should have worked and the 30 other reads and writes were refused, including reading customer scores, Airflow's connection and variable tables, `dag_run.conf`, MLflow's run tables and artifact paths, inserting, updating, deleting, truncating, dropping, creating tables or roles, and switching the session out of read-only mode and then inserting. Nothing was created or changed by those attempts.
 - **Drift check** (the `ml.monitor_drift` table and the **Drift** dashboard): for each snapshot, the population stability index (PSI) of every model input and of the churn probability, against the snapshot about a year earlier. Comparing with the same time of year matters: measured against the training period the churn probability scores 0.35 (scoring snapshot) and 0.41 (test snapshot), and quarter to quarter it reaches 1.26 at its worst step, with 7 of the 17 monitored columns above 0.25 at some quarter-to-quarter step, all purely from the seasons (the churn rate alone swings from 39% to 65%), so the usual thresholds would alert at once. Four columns are left out because they say nothing about customers: the three calendar columns (one value for the whole snapshot, so they always look drifted) and `tenure_days_capped` (it grows with how long the dataset has existed). The thresholds are the usual convention, 0.1 for a warning and 0.25 for an alert, and were not fitted to this data. **On the real data the newest same-season comparison (December 2010 against December 2011) has every monitored column `ok`, the largest PSI 0.022 and the churn probability 0.004**; the earlier comparisons are high because the first snapshots were built from a dataset that had only just begun. A snapshot with no snapshot a year earlier has no rows (there is nothing to compare it with yet). **The dataset is static, so real drift never happens here;** that the check detects drift is shown by tests that deliberately shift a snapshot, not by live data. Only the customers the models score are compared, in memory, and one number per column is stored.
 - **Demo traffic** (`python -m src.demo_traffic`): without callers the API dashboards are flat. The script sends synthetic requests for a few minutes, in a wave, with a small share that fail on purpose with a client error (an unknown customer, a malformed id, a route that does not exist) and none that can cause a server error. **It is not real usage:** every request carries the header `X-Demo-Traffic: true`, the API counts such requests under `traffic="demo"` (everything else is `traffic="real"`, which also includes the container's own health checks), and the Retail API dashboard has a panel that shows them apart. The label can only ever take those two values, whatever a caller sends, so it cannot grow the number of series. Run it with `docker compose run --rm app python -m src.demo_traffic --api-url http://api:8000 --minutes 5` (rebuild the image first: `docker compose build app`).
 - **Alert rules** (`services/grafana/provisioning/alerting/rules.yml`, nine rules in one group evaluated every 5 minutes, shown in Grafana under Alerting): the churn probability drifted a lot; model inputs drifted a lot; the newest version of a model was not promoted; a champion is older than 90 days; the latest Airflow run of a pipeline DAG failed; the API is serving an older churn or value model than the registry's champion (for 15 minutes); the API is not answering Prometheus (for 2 minutes); the API returned a server error. A firing rule is sent to Slack (next bullet). The 90 days and the 15 minutes are assumptions, not measured limits. The drift rules ask the drift table's own status, so the 0.25 lives in one place (`src/monitoring.py`). A rule whose queries cannot be evaluated is reported as an error and never hidden; no data counts as normal, except that the API being absent from Prometheus counts as an alert.
 - **Where alerts go:** one Slack channel, through an incoming webhook (`contactpoints.yml` and `policies.yml` next to the rules). Every rule goes to the same contact point, one message per rule, and a rule that keeps firing is repeated every 4 hours rather than every 5 minutes (4 hours is an assumption); a "resolved" message is sent too. The webhook address is a secret (whoever holds it can post in the channel), so it lives only in the git-ignored `.env` as `ALERT_WEBHOOK_URL`, reaches Grafana as an environment variable and is never written in a file (a test scans the whole project for one). It is optional: without it Grafana falls back to an address that cannot resolve (`alert-webhook-not-set.invalid`), still starts and still evaluates every rule, and each delivery fails visibly under Alerting > Contact points. **Checked by running it:** Grafana started both without and with the webhook, read the contact point and policy back with the address hidden, and its own test notification to the contact point reported `ok`. No real alert has been sent, because nothing is wrong, and the project does not fake one.
 - **Checked by running it (drift, demo traffic and alerts):** the real `monitor` stage wrote 68 drift rows (4 snapshot pairs by 17 columns); the Drift dashboard's queries ran through the live Grafana; the demo script ran against the real API for 90 seconds (377 requests: 349 successful, 22 not found, 6 malformed, no server errors) and Prometheus counted them as 378 demo against 8 real requests with 9 request series in all; all nine alert rules were evaluated through Grafana on the real data (all normal, for example drift 0.004, the champion 0.35 days old, the API serving version 5 as the registry does) and each was evaluated again with its threshold forced low to show that it fires. Grafana's own scheduler also evaluated all nine (health ok). A real alert has not fired, because nothing is wrong.
 - **Checked by running it (data dashboards):** the real `monitor` stage on the real warehouse and registry (8 snapshots, 30 score-distribution rows for 3 scoring runs, 4 segments, 15 model versions, 388 metrics, 16 backtest rows); the same stage as a task through the Airflow worker image (about 2.5 seconds); and every query of every panel of all three dashboards (29 panels) through the live Grafana, with no errors and no empty results. The read-only login was also tried on a simulated new machine (three empty databases): it succeeded, listed 15 skipped objects, granted what existed once the tables were created, and failed loudly on a renamed column.
 - **Not yet:** a real alert has not reached Slack (nothing has been wrong), and a failed Airflow task or GitHub Actions run does not post there. The API dashboard is nearly flat until the API has traffic, and the models do not change between retrains, because the dataset is static and training is deterministic. What does vary is the data itself across the eight snapshots (churn rate from 39% to 65%, average spend from about £330 to £870), which the data dashboards show.
